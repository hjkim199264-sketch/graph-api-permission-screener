## 2. 이 CSV에 없는 것 (그래서 못 하는 것)

M365 관리센터의 앱 등록 내보내기는 **Application 객체의 일부 속성만** 담는다.

| 빠진 필드 | 이게 없어서 못 하는 것 |
|---|---|
| `requiredResourceAccess` | **Graph API 권한 유무·목록 판정** ← 요청하신 "깡통 App" 정의의 핵심 |
| `owners` | **소유자 식별** ← 확인 메일 발송 대상 |
| `signInActivity` | 마지막 사용 시각 → 미사용 판정 |
| `appRoleAssignments` | 실제 관리자 동의로 **부여된** 앱 권한 |
| `oauth2PermissionGrants` | 실제 동의된 위임 권한 |

> **요청한 권한(requiredResourceAccess) ≠ 실제 부여된 권한(appRoleAssignment).**
> 앱 등록에 권한을 적어둬도 관리자 동의 전에는 실제로 동작하지 않는다.
> 회수 판단은 **실제 부여된 권한** 기준으로 해야 한다. 둘 다 수집해서 대조하는 이유다.

## 3. 이 CSV만으로 이미 나온 것 — 실측

499건 전수 분석 결과.

### 3-1. 자격증명 상태 — 가장 강한 깡통 신호

| 상태 | 건수 | 의미 |
|---|---:|---|
| **자격증명 없음** | **372 (75%)** | 인증서·시크릿이 하나도 없음 → **토큰 발급이 물리적으로 불가능** |
| 전부 만료 | 24 (5%) | 갱신 없이 방치됨 |
| 90일 내 만료 | 17 (3%) | 만료 임박 — 별도 안내 대상 |
| 유효 | 86 (17%) | 실제로 동작 가능한 앱 |

**자격증명이 없으면 앱은 어떤 경우에도 토큰을 받을 수 없다.** 권한 목록을 몰라도 이 372건은
"현재 사용 불가 상태"가 확정이다. 살아 있는 앱은 사실상 **86건**뿐이다.

### 3-2. 강한 깡통 후보

**자격증명 없음 + 리디렉션 URI 없음 = 351건 (70%)**

인증 수단도 없고 토큰을 돌려받을 주소도 없다. 만들다 만 앱이거나, 만든 주체가 사라진 앱이다.

### 3-3. ★ 가장 중요한 발견 — 미사용 앱의 정체

| tag | 건수 |
|---|---:|
| `AIAgentBuilder` / `AgentCreatedBy:CopilotStudio` / `AgenticApp` | **305 (61%)** |
| `Microsoft Fabric Identity` | 15 |

**전체 앱의 61%가 Copilot Studio가 자동 생성한 에이전트 앱이다.**

기존 PPT에는 미사용 앱 312개의 원인을 *"대부분 교육용 일시 계정이며 DX교육 시 사전 안내 강화"* 로 적어 두셨는데,
**305 ≈ 312** 로 숫자가 거의 일치합니다. 즉 실제 원인은 교육용 계정이 아니라
**Copilot Studio에서 봇을 만들 때 앱 등록이 자동 생성되고, 봇을 지워도 앱 등록은 남는 것**일 가능성이 높습니다.

원인이 다르면 대책도 달라집니다.

- 교육용이 원인이라면 → 사전 안내 강화
- **Copilot Studio가 원인이라면** → 개인이 소유자이므로 안내 메일이 무의미. 환경(Environment) 단위 정리 정책,
  봇 삭제 시 앱 등록 동반 삭제 절차, Copilot Studio 생성 권한 통제가 필요

**회수 안내 메일을 351건 일괄 발송하기 전에 이 305건의 성격부터 확인**하시길 권합니다.
대부분 "저는 봇 지웠는데요" 라는 회신이 돌아올 겁니다.

## 4. 빠진 데이터를 가져오는 방법

### 4-1. 앱 권한 · 소유자 · 실제 동의 내역 — 스크립트로 즉시 수집 가능

`tools/collect_entra_inventory.ps1` 을 만들어 두었습니다.

```powershell
Install-Module Microsoft.Graph -Scope CurrentUser
.\tools\collect_entra_inventory.ps1 -OutDir .\entra_export
```

**필요 권한(읽기 전용)**: `Application.Read.All` · `Directory.Read.All` · `AuditLog.Read.All`

> `Connect-MgGraph` 대화형 로그인은 **실행자 본인 권한으로 동작하는 Delegated 방식**이라
> 별도 Entra App 등록이나 앱 권한 부여가 필요 없습니다.
> 사내 기준으로는 접근범위 D → **G1**. 신청 절차 없이 운영그룹이 바로 돌릴 수 있습니다.

**산출물 5종**

| 파일 | 내용 |
|---|---|
| `01_applications.csv` | 앱별 요약 — Graph 권한 수·권한명·자격증명 상태·소유자 수·소유자 메일 |
| `02_requested_permissions.csv` | 앱 × 요청 권한 (GUID를 권한명으로 변환) |
| `03_owners.csv` | 앱 × 소유자 (이름·UPN·메일) ← **메일 발송 대상** |
| `04_granted_permissions.csv` | 실제 동의된 앱 권한 + 위임 권한 |
| `05_signin_activity.csv` | 서비스 주체별 마지막 로그인 시각 |

**주의**: `requiredResourceAccess` 안의 권한은 이름이 아니라 **GUID**로 저장됩니다.
스크립트가 Microsoft Graph 서비스 주체의 `appRoles` / `oauth2PermissionScopes`를 읽어
`Mail.Read` 같은 이름으로 변환합니다. 이 변환 없이는 CSV를 열어도 GUID만 보입니다.

### 4-2. 미사용 판정 — 로그인 활동

| 방법 | 경로 | 보존 | 비고 |
|---|---|---|---|
| **Graph 베타 리포트** | `GET /beta/reports/servicePrincipalSignInActivities` | — | 위 스크립트 `[4]` 단계에 포함 |
| 관리센터 UI | Entra > 엔터프라이즈 애플리케이션 > **사용량 및 인사이트** | 30일 | 수동 내보내기 |
| 로그인 로그 | Entra > 로그인 로그 > **서비스 주체 로그인** 탭 | 30일(P1) | CSV/JSON 다운로드 |

MS 권고 기준인 **90일 미사용 = 휴면**을 적용하려면 보존 기간이 30일보다 길어야 하므로,
로그인 로그를 **Log Analytics로 상시 내보내기**하는 구성이 필요합니다.

### 4-3. ★ 오용 탐지 — Graph 활동 로그 (지금 켜야 함)

*"어떤 앱이 실제로 어떤 Graph API를 호출했는가"* 를 알 수 있는 **유일한 소스**입니다.
기존 PPT의 *"이상활용(Key복제 통한 할당 App外 Graph API 호출, 사용목적과 다른 Graph API 호출) 확인"* 이
정확히 이 로그로 하는 일입니다.

**설정 (1회)**

1. Entra 관리센터 → **모니터링 및 상태** → **진단 설정** → 설정 추가
2. 로그 카테고리에서 **`MicrosoftGraphActivityLogs`** 체크
   (함께 권장: `AuditLogs`, `SignInLogs`, `ServicePrincipalSignInLogs`)
3. 대상: **Log Analytics 작업 영역** 선택 (없으면 Azure에서 먼저 생성)

**요구사항**: Microsoft Entra ID **P1 이상** · Azure 구독 + Log Analytics 작업 영역

> ⚠ **로그는 소급 수집되지 않습니다.** 진단 설정을 켠 시점부터 쌓입니다.
> 분기 모니터링을 '26.4Q에 하시려면 **지금 켜두셔야** 그때 3개월치 데이터가 있습니다.
> 이것 하나만은 다른 작업보다 먼저 해두시길 권합니다.

**KQL — 미사용 권한 찾기 (앱별 실제 호출 엔드포인트)**

```kusto
MicrosoftGraphActivityLogs
| where TimeGenerated > ago(90d)
| extend path = tostring(parse_url(RequestUri).Path)
| summarize calls = count(), lastCall = max(TimeGenerated),
            endpoints = make_set(path, 100)
        by AppId, ServicePrincipalId
| order by calls asc
```

→ 이 결과에 없는 앱 = 90일간 Graph 호출 0건 = **부여된 권한 전량 회수 대상**

**KQL — 오용 의심 (신청 목적과 다른 호출)**

```kusto
MicrosoftGraphActivityLogs
| where TimeGenerated > ago(30d)
| where AppId == "<대상 앱 ID>"
| extend path = tostring(parse_url(RequestUri).Path)
| summarize calls = count(), first = min(TimeGenerated), last = max(TimeGenerated)
        by RequestMethod, path, ResponseStatusCode
| order by calls desc
```

→ 신청서의 활용목적에 없던 엔드포인트가 나오면 소명 요청 대상

**KQL — 호출량 급증 탐지**

```kusto
MicrosoftGraphActivityLogs
| where TimeGenerated > ago(30d)
| summarize calls = count() by AppId, bin(TimeGenerated, 1d)
| summarize avg = avg(calls), max = max(calls) by AppId
| where max > avg * 5 and max > 1000
```

## 6. 메일 자동 발송에 대해

- **가능**: 소유자별 개인화 메일 초안 생성 (대상 앱 목록·권한 목록·회수 예정일 자동 삽입),
  `.eml` 파일 일괄 생성, Outlook 대량 발송용 CSV, 발송 PowerShell 스크립트
- **불가**: 제가 직접 테넌트에 인증해 발송하는 것 (자격 증명 없음)
- **비권장**: 검토 없는 일괄 자동 발송

세 번째가 중요합니다. 351건 중 상당수가 Copilot Studio 자동 생성 앱이라면, 일괄 발송은
**"쓰지도 않은 앱을 왜 나한테 묻느냐"** 는 회신 300건을 만듭니다.
소유자 없는 앱은 메일 자체가 나가지 않고요.

권장 형태는 **"도구가 대상 선정 + 초안 생성 → 담당자가 묶음 단위로 검토 후 발송"** 입니다.
Copilot Studio 앱처럼 성격이 같은 묶음은 개별 메일 대신 **공지 1건 + 이의신청 기간 운영**이 효율적입니다.
