## 1. 배경 (Background)

### 1-1. Microsoft Graph API란

Microsoft Graph는 M365(Teams, Outlook/Exchange, SharePoint, OneDrive, Entra ID, Intune 등)의 데이터를 단일 엔드포인트(`https://graph.microsoft.com`)로 조회·연계하는 통합 인터페이스다. 사내 활용 경로는 두 가지다.

1. **M365 서비스 기반 App** — Copilot Agent, Power Apps, SharePoint Online Page 등에 Graph API 권한을 부여하여 활용
2. **자체 개발 앱** — Web/API/Backend 앱을 Microsoft Entra에 등록한 뒤 Graph API 권한을 부여하여 활용

Graph API의 권한 모델은 두 축으로 나뉜다.

| 구분 | Delegated (위임) | Application (앱) |
|---|---|---|
| 실행 주체 | 로그인한 사용자 + 앱 | 사용자 없이 앱 단독 (데몬/배치) |
| 데이터 범위 | **로그인 사용자가 원래 접근 가능한 범위로 한정** | **테넌트 전체** (별도 제한 미적용 시) |
| 동의 | 사용자 동의 또는 관리자 동의 | 관리자 동의 필수 |
| 실효 권한 | min(앱 권한, 사용자 권한) | 앱 권한 그대로 |

즉 **Application 권한은 그 자체로 전사 데이터 접근권**이며, 이것이 등급 분류에서 접근 범위를 핵심 축으로 삼는 이유다.

### 1-2. 사내 추진 배경

- '26년 초부터 M365 데이터를 Graph API로 활용해 **DX 과제 산출물을 만들려는 요청이 급증**
- '25.6 기준 Entra 등록 App **502개**, 이 중 Graph API 권한 보유 **127개**, 부여된 권한 총 **1,101건**(App당 평균 약 9건)
- 이 중 **미호출 API 약 200건**, **생성 후 미사용 App 312개** — 권한이 부여만 되고 관리되지 않는 상태
- 요청 건마다 검토 기준이 달라 **판단 편차·리드타임 증가**, 요청자에게 되묻는 왕복(rework)이 반복

### 1-3. 현행 대응 프로세스

```
권한 요청 접수 → 요건 관리 → 권한 등급 분류 → 보안 검토 → 권한 할당
(요청자/DX기획/DX운영) (DX운영)   (DX운영)      (정보보호)   (요청자/M365운영)
```

수립된 기준(3기준 × 2값 = 8조합 → G1/G2/G3 3등급, 2차 판정 4지표)은 이미 존재하나, **적용이 전적으로 수기(手記)** 라는 것이 병목이다.

## 2. 문제 정의 (Problem Statement)

| # | 문제 | 근거 / 현상 | 영향 |
|---|---|---|---|
| P1 | **등급 판정이 담당자 역량에 의존** | 8조합 매핑 + 2차 4지표를 매번 수기 판단 | 동일 API가 요청 건마다 다른 등급 → 형평성 시비 |
| P2 | **신청서 품질 편차로 왕복 발생** | 템플릿 항목 미기재(권한 만료일, 정보주체 동의, 활용 데이터 필드 등) 빈발 | 접수→확정 리드타임 증가, 요청자 경험 저하 |
| P3 | **Application 권한 과대 신청** | 실제 요구는 "특정 사서함 1개"인데 `Mail.Read`(Application) 신청 → 테넌트 전 사서함 접근권 | 최소권한 원칙 위배, 사고 시 피해 범위 극대화 |
| P4 | **보안 검토 시점이 늦음** | 등급 분류 완료 후 정보보호그룹으로 넘어가야 보완사항 인지 | 후반 재작업, Committee 상정 지연 |
| P5 | **이력·메타데이터 관리 부재** | 요청 근거·판정 사유가 IR 본문에만 산재 | 분기 모니터링/회수 시 판단 근거 소실 |

> **핵심 문제**: 기준은 있으나 **기준을 적용하는 도구가 없다.**

## 5. 범위 (Scope)

### 5-1. In Scope

| # | 항목 |
|---|---|
| S1 | 신청 템플릿 PPTX(Full/약식 2종) 업로드 및 필드 자동 추출 |
| S2 | 1차 분류 — 정보유형(G/S) × 접근범위(D/A) × 작업유형(R/W) 8조합 → G1/G2/G3 |
| S3 | **접근범위 재판정 룰** — Application 신청이라도 특정 사서함/팀/사용자 한정 서술 시 Delegated 취급 |
| S4 | 2차 분류 — 데이터 최소화 / 정보주체 동의 / 저장·2차 가공 / 영향범위·규모 4지표 기반 상·하향 |
| S5 | Delete(X) 권한 포함 시 별도 협의 플래그 |
| S6 | 보완 요청사항 생성 (필수항목 누락 + 보안 리스크 + 최소권한 대안) |
| S7 | 향후 진행사항(다음 단계, 담당 조직, 예상 소요) 안내 |
| S8 | 판정 결과 JSON/텍스트 내보내기 (IR 회신문 붙여넣기용) |
| S9 | 사내 PC에서 **오프라인 단독 실행**(단일 HTML, 외부 CDN/서버 불필요) |

### 5-2. Out of Scope (v1)

| # | 항목 | 사유 |
|---|---|---|
| O1 | Entra ID / Graph API 실시간 연동(권한 자동 부여) | 권한 부여는 반드시 사람의 승인·결재를 거쳐야 함 |
| O2 | IT Request(IR) 시스템 직접 연동 | v2 검토 — v1은 결과 텍스트 복사·붙여넣기로 대응 |
| O3 | 서버·DB 구축, 사용자 인증 | 판정 도구 성격상 불필요. 파일은 브라우저 내에서만 처리(외부 전송 없음) |
| O4 | 슬라이드 내 이미지(데이터 흐름도/구현화면) 자동 해석 | 이미지 첨부 **여부**만 확인, 내용 해석은 담당자 육안 검토 |
| O5 | 분기 모니터링·미사용 권한 회수 자동화 | 별도 과제 (`[참고] Entra App / Graph API 모니터링 방안`) |

## 6. 현재 분류 기준 (As-Is 기준 정리)

### 6-1. 1차 분류 — 3기준 × 2값 = 8조합

| 기준 | 값 | 코드 | 정의 | 예시 |
|---|---|---|---|---|
| **① 정보 유형**<br>(어떤 데이터?) | 일반 정보 | **G** | 민감 정보 外 Graph API 연동 가능 M365 정보 | 조직도, 메일 주소, 부서/직급, Teams 팀 목록, 라이선스 현황 |
| | 민감 정보 | **S** | *High*: 개인정보·기업 기밀이 **직접 포함**<br>*Low*: 기밀·개인정보를 **유추 가능** | *High*: 메일 본문, 첨부 원문, Teams 채팅, SPO 문서 원본<br>*Low*: 메일 제목, 첨부파일명, SPO 문서명, 채팅 목록, 접속 기록, 상세 일정 |
| **② 접근 범위**<br>(누구의 데이터?) | 개인/특정 계정 | **D** | Delegated — 개인 계정이 접근 가능한 정보 내 활용 | 개인 권한으로 수기 접근하는 Outlook/Teams/Power BI 정보를 자동 처리 |
| | 전사 계정 | **A** | Application — 전사 M365 정보 내 활용 | 전사 범위 데이터 활용/가공/자동화 |
| **③ 작업 유형**<br>(어떤 작업?) | Read | **R** | 데이터 표시·적재 (일방향) | Power BI/SPO 대시보드, 협업지수 산출 |
| | Create/Update | **W** | 데이터 변경·업로드·발신 (양방향) | 결재 완료 알림, 인사발령 시 라이선스 할당 |
| | *(Delete)* | **X** | 운영 관리 전용, 현업 부여 제외 | 퇴직자 라이선스 제거, 기간 경과 메일/팀 삭제 |

### 6-2. 8조합 → 3등급 매핑

| # | 조합 | 정보 | 범위 | 작업 | **등급** | 할당 프로세스 |
|---|---|---|---|---|---|---|
| 1 | GDR | 일반 | 개인 | Read | **G1** | 운영그룹 주관, 필요시 보호그룹 공유 |
| 2 | GDW | 일반 | 개인 | Write | **G1** | 〃 |
| 3 | SDR | 민감 | 개인 | Read | **G1** | 〃 |
| 4 | SDW | 민감 | 개인 | Write | **G1** | 〃 |
| 5 | GAR | 일반 | 전사 | Read | **G2** | 운영그룹 주관 + 보호그룹 공유 |
| 6 | GAW | 일반 | 전사 | Write | **G2** | 〃 |
| 7 | SAR | 민감 | 전사 | Read | **G3** | 보안 요건 충족 후 운영성 검토 |
| 8 | SAW | 민감 | 전사 | Write | **G3** | 〃 |

> **판정 규칙의 본질**: 접근 범위가 **Delegated면 정보 민감도와 무관하게 G1**(사용자 본인 권한 범위를 넘지 못하므로). **Application일 때만** 정보 유형이 G2/G3를 가른다.
>
> ※ `X`(Delete) 포함 시 등급과 별개로 **별도 협의** 대상.

### 6-3. 2차 분류 — 활용 방식 기반 4개 판단 지표

| 기준 | 설명 | 사례 | 조정 |
|---|---|---|---|
| **데이터 최소화**<br>(필터링/마스킹) | 非필수 컬럼 제외 로직 구현 | `Mail.ReadWrite` 中 메일 본문 Field 제외 로직 구현 | **G3 → G2** 하향 |
| **정보주체 인지/동의** | Target Data Owner 전원이 저장·2차 활용을 인지/동의 | SPO 시황정보 적재를 전 사용자가 인지 | **G2 → G1** 하향 |
| **저장·2차 가공** | 저장 여부, 적재량/주기, 2차 활용(통계 분석 등) 여부 | 채팅 데이터를 저장 없이 통계만 활용 | **G3 → G2** 하향 |
| **영향 범위/활용 규모**<br>(Scope/Volume) | 영향 계정의 중요도·수, 사용 빈번도·영향도 | 직책자 M365 활동지수를 소속 임원에게 Daily 메일 발송 | **G2 → G3** 상향 |

| 11 | 프로젝트 효율화 모바일 - OneDrive 접근 | "전체 열람 권한이 아닌, **로그인한 사용자가 열람 권한이 있는 파일만** 열람 가능하도록 제한하여 허용" |
| 10 | 발전소 Tech-Advisor 앱 | "**공유 사서함**과 Graph API 요청 → 공유 사서함만 선 발급, Graph API 미발급" |

또한 템플릿 예시(슬라이드 5·11) 자체가 이 케이스를 담고 있다.

> `① API명/활용목적`: **Mail.Read : 특정 사서함을 통한 시스템 알람 메일링 목표**
> `①Delegated/Application`: **Application**
> `①활용계정/App`: **특정 공유사서함**

→ 신고값은 Application(= SAR → **G3**)이지만, 실제 활용 대상은 공유 사서함 1개다. 이 경우 접근범위를 **D로 재판정하여 SDR → G1**로 낮추되, **"Application 권한은 기본적으로 전 사서함 접근이 가능하므로 기술적 범위 제한을 반드시 적용"** 을 보완 요청사항으로 강제한다.

**제시할 기술적 범위 제한 수단**

| 워크로드 | 수단 | 비고 |
|---|---|---|
| Exchange Online (메일) | **RBAC for Applications** (권장) / `New-ApplicationAccessPolicy` | 앱의 Application 권한을 메일 사용 보안 그룹 범위로 한정. ApplicationAccessPolicy는 MS가 RBAC for Applications로 대체 안내 중 |
| SharePoint / OneDrive | **`Sites.Selected`** 권한 + 사이트별 권한 부여 | `Sites.Read.All`/`Sites.ReadWrite.All` 대신 사용 |
| Teams | **RSC**(Resource-Specific Consent), `ChannelMessage.Read.Group` 등 `.Group` 계열 | 특정 팀에만 동의 |
| 공통 | Delegated 권한 전환 | 사용자 로그인 컨텍스트가 있는 경우 최우선 대안 |

## 9. 가정 및 제약 (Assumptions & Constraints)

### 가정

- A1. 요청자는 배포된 **표준 신청 템플릿 PPTX**(Full 또는 약식)를 사용한다.
- A2. 템플릿의 라벨 문구(`과제명`, `① API명/활용목적`, `①Delegated/Application` 등)는 임의 변경되지 않는다.
- A3. API 명칭은 Microsoft Graph 공식 권한명(`Mail.Read`, `Sites.ReadWrite.All` 등)으로 기재된다.
- A4. 민감 정보 상세 기준은 **정보보호그룹 의견 반영 후 최종 확정** 예정이며, v1은 PPT 정의를 준용한다.

### 제약

- C1. 사내 PC 브라우저(Edge/Chrome, Chromium 기반)에서 실행. 서버·설치 불가.
- C2. 외부 네트워크 호출 금지 — 라이브러리 CDN 사용 불가, 전 로직 단일 HTML에 인라인.
- C3. 신청서에 개인정보/기밀이 포함될 수 있으므로 **파일은 절대 외부 전송 금지**.
- C4. `.ppt`(레거시 바이너리)는 미지원 — `.pptx`만 지원.
- C5. **판정 결과는 초안**이며, 권한 부여의 최종 승인권은 정보보호그룹 및 IR 결재선에 있다.

## 10. 리스크 (Risks)

| ID | 리스크 | 영향 | 대응 |
|---|---|---|---|
| R1 | 자동 판정을 맹신하여 담당자 검토가 형해화 | 오판정 그대로 권한 부여 | 화면·출력물 전면에 "초안" 명시, 근거 문장 항상 병기, G3는 자동 승인 경로 없음 |
| R2 | 템플릿 라벨 변경/셀 병합 변형으로 파싱 실패 | 항목 누락 → 오판정 | 라벨 기반 유연 매칭 + **추출 결과 화면 표시 후 수기 보정 허용** |
| R3 | API 사전에 없는 신규/베타 권한 | 정보유형 판정 불가 | `미확인` 처리 + 보수적으로 S(민감) 가정 + 수동 지정 UI 제공 |
| R4 | BR-3 재판정의 오탐(false positive) | 실제 전사 접근인데 G1로 하향 | 재판정 시 **범위 제한 기술 조치 이행을 필수 조건으로 부착**, 미이행 시 원등급 환원 명시 |
| R5 | 민감 정보 기준 미확정 | 정보보호그룹 확정 시 사전 재작업 | API 사전을 별도 JSON 블록으로 분리하여 수정 용이하게 구성 |
| R6 | 판정 이력이 로컬에만 남아 유실 | 사후 추적 불가 | JSON 내보내기 → 요청 대장/IR 첨부를 운영 규칙화 |
