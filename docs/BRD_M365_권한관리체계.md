## 1. 배경

### 1-1. 권한 요청은 세 갈래로 들어온다

| 유형 | 대상 | 실제 사례 |
|---|---|---|
| **Graph API 권한** | Entra 등록 앱에 부여하는 M365 데이터 접근 권한 | 법무 DB 구축, HR Peer 서비스, MI 구축, RPA 자동화 |
| **M365 관리자 역할** | 관리 센터에서 관리 작업을 수행하는 사전 정의 권한 | SharePoint 관리자, Teams 앱 등록, Azure 구독 Owner |
| **기 부여 권한의 사후 관리** | 이미 나간 권한·앱의 회수 | 미사용 앱 정리, 미호출 API 회수 |

기존 체계는 **첫 번째만** 다뤘다. 두 번째는 기준 자체가 없어 담당자 재량이었고,
세 번째는 계획만 있고 도구가 없었다.

### 1-2. Graph API — 권한 모델의 본질

Graph API는 M365 데이터를 단일 엔드포인트(`https://graph.microsoft.com`)로 접근하는 인터페이스다.
권한 모델은 두 축으로 나뉜다.

| 구분 | Delegated (위임) | Application (앱) |
|---|---|---|
| 실행 주체 | 로그인한 사용자 + 앱 | 사용자 없이 앱 단독 (데몬/배치) |
| 데이터 범위 | **로그인 사용자가 원래 접근 가능한 범위로 한정** | **테넌트 전체** (별도 제한 미적용 시) |
| 동의 | 사용자 또는 관리자 동의 | 관리자 동의 필수 |
| 실효 권한 | min(앱 권한, 사용자 권한) | 앱 권한 그대로 |

**Application 권한은 그 자체로 전사 데이터 접근권**이다. 이것이 등급 분류에서
접근 범위를 핵심 축으로 삼는 이유다.

### 1-3. 관리자 역할 — 규모와 편차

Microsoft Entra 기본 제공 역할은 **136종**(M365 관리센터 노출 기준)이며,
이 중 Microsoft가 「권한 있는 역할(Privileged role)」로 표시한 것이 **36종**이다.

역할마다 영향 범위와 위험도가 극단적으로 다르다.
전역 관리자는 테넌트 전체에 무제한 권한을 갖는 반면, 보고서 읽기 권한자는 사용 현황 조회만 가능하다.
**같은 "관리자"라는 이름을 달고 있으나 위험도는 수십 배 차이가 난다.**

### 1-4. 현황 수치

| 항목 | 수치 | 출처 |
|---|---|---|
| Entra 등록 앱 | **499건** | 관리센터 내보내기 (2026-08-06) |
| 그중 Graph API 권한 보유 | 127건 | 원본 PPT ('25.6 기준) |
| 부여된 Graph API 권한 | 1,101건 (앱당 평균 약 9건) | 원본 PPT |
| 미호출 API | 약 200건 | 원본 PPT |
| **자격증명이 하나도 없는 앱** | **372건 (75%)** | CSV 실측 |
| **자격증명·리디렉션 URI 모두 없는 앱** | **351건 (70%)** | CSV 실측 |
| **Copilot Studio 자동 생성 앱** | **305건 (61%)** | CSV 실측 |
| 실제로 동작 가능한 앱 | **86건 (17%)** | CSV 실측 |
| 관리자 역할 요청 처리 이력 | 12건 (6개월) | 요청 대장 |

> **자격증명이 없으면 토큰 발급이 물리적으로 불가능하다.** 권한 목록을 몰라도
> 372건은 "현재 사용 불가"가 확정이며, 살아 있는 앱은 86건뿐이다.

### 1-5. 현행 프로세스

```
권한 요청 접수 → 요건 관리 → 권한 등급 분류 → 보안 검토 → 권한 할당
(요청자/DX기획/DX운영) (DX운영)  (DX운영)      (정보보호)   (요청자/M365운영)
```

Graph API에 대한 기준(8조합 → G1/G2/G3, 2차 4지표)은 수립되어 있으나
**적용이 전적으로 수기(手記)** 라는 것이 병목이었다.

## 2. 문제 정의

| # | 문제 | 근거 / 현상 | 영향 |
|---|---|---|---|
| **P1** | Graph API 등급 판정이 담당자 역량에 의존 | 8조합 + 2차 4지표를 매번 수기 판단 | 동일 API가 건마다 다른 등급 → 형평성 시비 |
| **P2** | 신청서 품질 편차로 왕복 발생 | 권한 만료일·정보주체 동의·활용 필드 미기재 빈발 | 리드타임 증가, 요청자 경험 저하 |
| **P3** | Application 권한 과대 신청 | 실제 요구는 "특정 사서함 1개"인데 `Mail.Read`(Application) 신청 | 최소권한 위배, 사고 시 피해 범위 극대화 |
| **P4** | 보안 검토 시점이 늦음 | 등급 분류 후에야 보완사항 인지 | 후반 재작업, Committee 상정 지연 |
| **P5** | **관리자 역할은 기준 자체가 없음** | 136종의 위험도 편차가 문서화되지 않음 | 전역 관리자 과다 부여 위험, 판단 근거 부재 |
| **P6** | **사후 관리 도구 부재** | 미사용 앱 351건 · 미호출 API 200건이 방치 | 자격 증명 유출 시 침해 경로 |
| **P7** | **미사용 앱의 원인 오진** | "교육용 일시 계정"으로 기록됐으나 실제는 Copilot Studio 자동 생성 (61%) | 잘못된 대책 수립 → 정리해도 재발 |
| **P8** | 이력·판정 근거 소실 | 판정 사유가 IR 본문에만 산재 | 분기 모니터링·회수 시 근거 부재 |

> **핵심 문제**: Graph API는 기준은 있으나 적용 도구가 없었고,
> 관리자 역할은 기준 자체가 없었으며, 사후 관리는 데이터조차 확보되지 않았다.

## 6. 등급 체계

세 체계 모두 **3기준 × 2값 = 8조합 → 3등급** 이라는 같은 골격을 쓴다.
**한 축이 등급을 결정**하는 구조도 공유한다.

### 6-1. Graph API — G1/G2/G3

| 기준 | 값 |
|---|---|
| ① 정보 유형 | **G** 일반 / **S** 민감 |
| ② 접근 범위 | **D** 개인·Delegated / **A** 전사·Application |
| ③ 작업 유형 | **R** Read / **W** Create·Update / *(X Delete → 별도 협의)* |

```
GDR · GDW · SDR · SDW  →  G1  개인 권한 정보 활용
GAR · GAW              →  G2  전사 일반 정보 활용
SAR · SAW              →  G3  전사 민감 정보 활용
```

> **접근 범위가 Delegated면 정보 민감도와 무관하게 G1.**
> 앱이 사용자 본인의 권한 범위를 넘지 못하기 때문이다.
> Application일 때만 정보 유형이 G2와 G3를 가른다.

**2차 분류** — 데이터 최소화(G3→G2) · 정보주체 동의(G2→G1) · 비저장(G3→G2) · 영향범위·규모(G2→G3).
하향은 **최대 1등급**, 상향은 제한 없음.

### 6-2. 관리자 역할 — A1/A2/A3

| 기준 | 값 |
|---|---|
| ① 영향 범위 | **S** 서비스·기능 한정 / **T** 테넌트 전역 |
| ② 작업 유형 | **R** 읽기 전용 / **W** 구성 변경 |
| ③ 민감 자산 접근 | **N** 없음 / **P** 있음 |

**민감 자산 접근(P)** 은 다음 중 하나라도 해당할 때다.

- **(a) 권한 상승** — 역할 할당, 자격 증명·MFA 변경, 앱 권한 동의, 조건부 액세스·인증 정책 변경, 도메인·페더레이션 변경
- **(b) 콘텐츠 접근** — 메일·파일·채팅·문서 원문 열람 또는 열람 위임 설정 가능

```
민감 접근 P 있음          →  A3   (범위·작업과 무관)
N + 읽기(R) + 서비스(S)   →  A1
N + 읽기(R) + 전역(T)     →  A2
N + 변경(W) + 서비스(S)   →  A2
N + 변경(W) + 전역(T)     →  A3
```

판정 결과 — **A3 65건(47%) · A2 58건(42%) · A1 13건(9%)**

> A3 비중이 높은 것은 관리자 역할 다수가 구조적으로 권한 상승 또는 콘텐츠 접근 경로를 갖기 때문이며,
> 관리자 역할 요청을 Graph API보다 엄격히 통제해야 하는 근거가 된다.

### 6-3. Entra App 회수 — D1~D4

| | 판정 | 조건 |
|---|---|---|
| **D1** | 즉시 삭제 후보 | 자격증명·리디렉션 URI·Graph 권한 전무 + 방치 기준 경과 |
| **D2** | 소유자 확인 필요 | 자격증명 없음/만료이나 구성 요소 잔존 |
| **D3** | 권한 회수 대상 | Graph 권한 보유 + 미사용 또는 인증 불가 |
| **D4** | 유지 | 유효 자격증명 + 최근 사용 |

보안 플래그(MT 멀티테넌트 · PA 개인계정 · IMP 암묵적 흐름 · EXP 만료 임박 · DEAD 만료 · NOOWNER 소유자 없음)는
처분과 별개로 병행 점검한다.

## 7. 접근범위 재판정 룰 (핵심 요구사항)

> **Application 권한으로 신청했더라도, 「특정 사서함」·「특정 팀」·「공유 사서함」·「로그인한 사용자」 등
> 대상 한정 서술이 있으면 접근범위를 Delegated로 재판정한다.**

### 7-1. 근거 — 이미 실무에서 반복되던 패턴

| 이력 | 요청 | 실제 처리 |
|---|---|---|
| 3번 | 개발자 사서함 접근 & 공사일보 수집 | "현업 담당자 **1인의 메일 사서함 및 SharePoint에만** 접근 가능한 권한으로 제한" |
| 8번 | RPA 자동화 Graph API | "**로그인 된 특정 사용자의** 메일, SPO만 접근 가능한 제한적 권한으로 승인" |
| 11번 | 프로젝트 효율화 모바일 OneDrive | "전체 열람 권한이 아닌, **로그인한 사용자가 열람 권한이 있는 파일만**" |
| 10번 | 발전소 Tech-Advisor | "**공유 사서함**과 Graph API 요청 → 공유 사서함만 선 발급" |

템플릿 예시(슬라이드 5·11) 자체도 이 케이스다 —
`Mail.Read : 특정 사서함을 통한 시스템 알람 메일링` / 권한유형 `Application` / 활용계정 `특정 공유사서함`.

### 7-2. 반드시 함께 걸어야 하는 조건

**Application 권한은 별도 제한이 없으면 실제로는 테넌트 전체에 적용된다.**
"특정 사서함만 쓰겠다"는 선언은 애플리케이션 코드 레벨의 약속일 뿐,
**부여된 권한 자체를 좁히지 않는다.**

따라서 재판정으로 낮아진 등급은 **아래 기술적 범위 제한 조치의 이행을 전제 조건**으로 하며,
미이행 시 원 등급으로 환원한다.

| 워크로드 | 조치 |
|---|---|
| Exchange Online | **RBAC for Applications**(권장) 또는 `New-ApplicationAccessPolicy` |
| SharePoint/OneDrive | **`Sites.Selected`** + 대상 사이트에만 권한 부여 |
| Teams | **RSC**(Resource-Specific Consent) 또는 `*.Group` 계열 권한 |
| 공통 | 사용자 로그인 컨텍스트가 있으면 **Delegated 전환** (최우선 대안) |

`전사`·`전체 사용자`·`전 임직원` 등 전사 표현이 함께 있으면 재판정하지 않고 **범위 상충**으로 표시한다.

## 10. 가정 및 제약

### 가정

- A1. 요청자는 배포된 **표준 신청 템플릿 PPTX**를 사용한다.
- A2. 템플릿 라벨 문구는 임의 변경되지 않는다.
- A3. API 명칭은 Microsoft Graph 공식 권한명으로 기재된다.
- A4. **민감 정보 상세 기준은 정보보호그룹 확정 후 반영** 예정이며, 현재는 원본 PPT 정의를 준용한다.
- A5. 관리자 역할 목록은 Microsoft Entra 기본 제공 역할 기준이며, MS의 역할 추가·변경 시 갱신이 필요하다.
- A6. 인벤토리 수집 스크립트는 담당자가 직접 실행한다 (모듈 설치·로그인이 대화형).

### 제약

- C1. 사내 PC 브라우저(Edge/Chrome) 실행. 서버·설치 불가.
- C2. 외부 네트워크 호출 금지 — CDN 사용 불가, 전 로직 단일 HTML 인라인.
- C3. 신청서·인벤토리에 개인정보·기밀 포함 가능 → **파일 외부 전송 절대 금지**.
- C4. `.ppt`(레거시), DRM/IRM 암호화 파일 미지원.
- C5. **판정 결과는 초안**. 최종 승인권은 정보보호그룹 및 IR 결재선에 있다.
- C6. **메일은 초안 생성까지만.** 발송은 담당자가 검토 후 직접 수행한다.
- C7. Graph 활동 로그는 **Entra ID P1 이상 + Log Analytics**가 필요하며 **소급 수집되지 않는다**.
