## 1. 제품 개요

### 1-1. One-liner

> **권한 요청의 접수부터 회수까지 — 신청서를 올리면 등급이, 역할명을 치면 위험도가,
> 인벤토리를 올리면 회수 대상과 확인 메일이 나오는 오프라인 단일 페이지 도구.**

### 1-2. 3탭 구조

| | 구간 | 대상 | 등급 | 입력 | 출력 |
|---|---|---|---|---|---|
| **Tab 1** | 사전 심사 | Graph API 권한 | G1/G2/G3 | 신청 템플릿 PPTX | 등급 · 보완요청 · 진행절차 · IR 회신문 · **보안검토 요청 메일** |
| **Tab 2** | 사전 심사 | M365 관리자 역할 | A1/A2/A3 | 역할 검색·선택 | 등급 · 위험도 · 핵심 리스크 · PIM 방식 · 승인 절차 |
| **Tab 3** | 사후 정리 | Entra App 회수 | D1~D4 | 인벤토리 CSV | 처분 등급 · 보안 플래그 · **소유자별 확인 메일** |

### 1-3. 설계 원칙

| # | 원칙 | 구현 |
|---|---|---|
| D1 | **결정적(deterministic)** | 규칙 기반. AI/확률 추론 없음 → 동일 입력 = 동일 출력, 감사 가능 |
| D2 | **근거 제시** | 모든 판정에 발동 규칙 ID와 원문 근거 병기 |
| D3 | **초안일 뿐** | 전면 DRAFT 배지. 자동 승인·자동 발송 경로 없음 |
| D4 | **보수적 기본값** | 미확인·모호 항목은 높은 등급 쪽으로 가정하고 확인 요청 |
| D5 | **오프라인·무전송** | 외부 요청 0건. 업로드 파일은 메모리에서만 처리 |
| D6 | **수기 보정 허용** | 파싱 결과를 화면에서 수정하면 즉시 재판정 |
| D7 | **한계를 숨기지 않음** | 데이터가 없으면 "없어서 못 한다"를 화면에 명시 (Tab 3 커버리지) |
| D8 | **단일 원본** | 관리자 역할 데이터는 파일 하나가 PPT·Excel·HTML의 원본 |

# Tab 1 — Graph API 권한 판정

## 3. 처리 흐름

```
[PPTX 업로드]  브라우저 내에서만 처리
      ▼
[1] ZIP 해제 → ppt/slides/slideN.xml
[2] 표(a:tbl)·텍스트박스 파싱 → 라벨 기반 필드 매핑
[3] API 항목 분해 (①②③… 복수 API 지원)
[4] 1차 분류 : 정보유형(G/S) × 접근범위(D/A) × 작업유형(R/W/X) → 8조합 → G1/G2/G3
      └─ ★ 접근범위 재판정 룰 (RULE-SCOPE-D)
[5] 2차 분류 : 4개 판단 지표로 상·하향
[6] 종합 등급 = MAX(API별 등급)
[7] 보완 요청사항 (누락 / 최소권한 / 고위험 / 운영위생)
[8] 향후 진행사항
      ▼
[결과 + IR 회신문 + 보안검토 요청 메일 + JSON]
```

## 4. 기능 요구사항

### FR-1. 파일 입력

| ID | 요구사항 |
|---|---|
| FR-1.1 | `.pptx` 드래그&드롭 또는 파일 선택 |
| FR-1.2 | 브라우저 내에서만 처리. 네트워크 요청 0건 |
| FR-1.3 | `.ppt`(레거시), DRM/IRM 암호화 파일은 명확한 안내와 함께 거부 |
| FR-1.4 | 전 슬라이드 스캔, 템플릿 표 자동 식별 |
| FR-1.5 | 샘플 데이터로 즉시 체험 |

**DRM 판별**: 파일 선두 4바이트가 `D0 CF 11 E0`(OLE Compound File)이면 암호화로 간주.

**압축 해제**: 네이티브 `DecompressionStream('deflate-raw')` 우선, 미지원 시 자체 inflate 폴백.
두 경로의 출력이 바이트 단위로 일치함을 검증 완료(TC-17).

### FR-2. 필드 추출

**라벨 기반 매칭** — 셀 위치가 아닌 라벨 문구로 찾아 Full/약식 및 행 순서 변경에 대응.

| 정규화 필드 | 매칭 라벨 (공백·`*`·원문자 제거 후) |
|---|---|
| `taskName` | 과제명, 프로젝트명 |
| `taskOverview` | 과제개요, 개요 |
| `requester` / `developer` | 요청자/부서, 개발자/소속 |
| `api[n].nameAndPurpose` | ①API명/활용목적, ①요청API명/활용목적 |
| `api[n].data` | ①활용데이터/URL |
| `api[n].appId` | ①EntraAPPID |
| `api[n].permType` | ①Delegated/Application |
| `api[n].account` | ①활용계정/App |
| `scopeVolume` / `consent` / `storage` | 영향범위/활용규모, 정보주체인지/동의, 저장/2차가공 |
| `remark` / `expiry` | 비고, 권한만료일 |

**값 추출 규칙**

1. 라벨 셀 기준 **같은 행 오른쪽으로 스캔**, 첫 비어있지 않은 셀 채택 (병합 셀 대응)
2. 다음 라벨을 만나면 중단 → 값 없음
3. 오른쪽에 없으면 아래 행 같은 열 확인 (세로형 대응)
4. 표 밖 텍스트에서 `라벨 : 값` 보조 추출 (단, `*`·`※` 시작 안내문은 제외)

**복수 API**: 원문자(`①②③④⑤`) 또는 숫자 접두로 슬롯 분리.

**공백 판정**: `T.B.D`, `미정`, `-`, `?` 등은 미기재.
단 **`consent`/`storage`에서 `N/A`·`없음`은 의미 있는 값**이므로 별도 정규식(`RE_BLANK_STRICT`) 적용.

### FR-3. 1차 분류

#### FR-3.1 정보 유형 (G / S)

내장 API 사전으로 판정. 슬라이드 7의 23건이 정본, 동일 리소스 패밀리로 확장.

| infoType | 의미 | 근거 |
|---|---|---|
| `G` | 일반 정보 확정 | 슬라이드 7에서 `G1/G2` 또는 `G2` 표기 |
| `S` | 민감 정보 확정 | 슬라이드 7에서 `G3` 표기 |
| `GS` | 활용 데이터에 따라 결정 | 슬라이드 7에서 `G2/G3` 표기 → **보수적으로 S 가정** |

사전 미등재 → `UNKNOWN` → **S 가정** + 수동 지정 요청.

#### FR-3.2 접근 범위 (D / A) — ★ 핵심 룰

```
declared = Delegated   → D
declared = Application → RULE-SCOPE-D 평가
```

**평가 대상**: 해당 API 슬롯의 `nameAndPurpose` + `data` + `account`

**발동 키워드(LIMIT)**: 특정 사서함 · 공유 사서함 · 특정 팀 · 특정 채널 · 특정 사이트 ·
특정 사용자 · 특정 계정 · 로그인한 사용자 · 본인 계정 · 담당자 1인 · `Sites.Selected` 등

**차단 키워드(TENANT)**: 전사 · 전체 사용자 · 모든 사용자 · 전 임직원 · 테넌트 전체 · 모든 팀 등

| LIMIT | TENANT | 결과 |
|---|---|---|
| O | X | **D로 재판정** + 근거 문장 표시 + `SEC-SCOPE` **필수** 부착 |
| O | O | **A 유지** + `SEC-CONFLICT` (범위 상충) |
| X | — | A 유지 |

**부착되는 필수 조건 (`SEC-SCOPE`)**

> 재판정으로 하향된 등급은 **기술적 범위 제한 조치의 이행을 전제**로 한다. 미이행 시 원 등급 환원.

| 워크로드 | 조치 |
|---|---|
| Exchange Online | RBAC for Applications(권장) / `New-ApplicationAccessPolicy` |
| SharePoint/OneDrive | `Sites.Selected` + 대상 사이트 지정 |
| Teams | RSC / `*.Group` 계열 |
| 공통 | Delegated 전환 (최우선) |

#### FR-3.3 작업 유형 (R / W / X)

| 판정 | 조건 (우선순위 순) |
|---|---|
| **X** | 권한명에 `Delete`/`Purge`, 또는 활용목적에 삭제·제거·회수·파기·퇴직 등 |
| **W** | `ReadWrite`, `.Write`, `.Send`, `.Create`, `.Manage`, `FullControl` 등 |
| **R** | 그 외 |

`X`는 등급을 바꾸지 않고 **별도 협의 플래그**를 세운다.
`ReadWrite` 계열은 삭제를 내포하므로 `NOTE-RW-DELETE` 안내.

#### FR-3.4 8조합 매핑

| 조합 | 등급 | | 조합 | 등급 |
|---|---|---|---|---|
| `GDR` `GDW` `SDR` `SDW` | **G1** | | `GAR` `GAW` | **G2** |
| | | | `SAR` `SAW` | **G3** |

구현: `범위 D → G1` / `A && G → G2` / `A && S → G3`

### FR-4. 2차 분류

| 규칙 ID | 지표 | 조정 |
|---|---|---|
| `ADJ-MIN` | 데이터 최소화 (필터링·마스킹·필드 제외) | G3 → G2 |
| `ADJ-CONSENT` | 정보주체 인지/동의 확보 | G2 → G1 |
| `ADJ-STORE` | 저장 없이 통계·집계만 | G3 → G2 |
| `ADJ-SCOPE-UP` | 영향범위·규모 (중요계정 또는 전사×고빈도) | G2 → G3 |

**적용 정책**

1. 하향은 **최대 1등급**. 2건 이상 발동 시 `ADJ-CAP` 안내.
2. 조정 순서는 **하향 먼저, 상향 나중**. G3 →(`ADJ-MIN`)→ G2 →(`ADJ-SCOPE-UP`)→ G3 는 의도된 동작.
3. `ADJ-SCOPE-UP`은 **G2 → G3 자동 상향만**. G1은 안내만 하고 자동 상향하지 않는다.
4. 상향·하향 동시 발동 시 **상쇄** + `ADJ-OFFSET` 담당자 확인 표시.
5. 모든 조정에 규칙 ID + 근거 원문 출력.
6. 미기재는 조정하지 않는다 (미기재 ≠ 유리한 해석).
   단 `storage: N/A` → 비저장, `consent: N/A` → 동의 미확보로 해석하고
   후자는 최종 등급에 따라 심각도를 달리한다 (G2 이상 `Blocker` / G1 `High`).

### FR-5. 종합 등급

```
overallGrade = MAX(api[i].finalGrade)
```
`별도 협의(X)` 플래그가 하나라도 있으면 신청 건 전체에 표시.

### FR-6. 보완 요청사항

심각도 4단계: `Blocker`(접수 보류) / `Critical` / `High` / `Medium`

**A. 필수 항목 누락 — Blocker**
`REQ-BASIC` · `REQ-EXPIRY` · `REQ-API` · `REQ-PURPOSE` · `REQ-PERMTYPE` · `REQ-DATA` ·
`REQ-CONSENT` · `REQ-CONSENT-NO`(등급 연동) · `REQ-STORE`

**B. 최소권한 — High**
`SEC-SCOPE`(재판정 시 필수) · `SEC-CONFLICT` · `SEC-ALL` · `SEC-OVERPERM` · `SEC-UNDERPERM` ·
`SEC-MAILSEND` · `SEC-SITES` · `SEC-FILES` · `SEC-TEAMSRSC`

**C. 고위험 — Critical**
`RISK-PRIVESC`(권한 상승 경로) · `RISK-IMPERSONATE`(사칭 발신) · `RISK-MASSREAD`(전사 콘텐츠 열람) ·
`RISK-DELETE` · `RISK-UNKNOWN`

**D. 운영·보안 위생 — Medium**
`OPS-EXPIRY-LONG` · `OPS-AUTH`(Managed Identity 권고) · `OPS-STORE-DETAIL` · `OPS-DIAGRAM` ·
`OPS-ENV` · `OPS-MONITOR` · `NOTE-RW-DELETE` · `NOTE-NOSTORE` · `NOTE-SPO-SENSITIVE` · `REQ-FIELD`

### FR-7. 향후 진행사항

| 등급 | 절차 | 담당 | 소요 |
|---|---|---|---|
| **G1** | 요건 확정 → 운영그룹 수행 → (필요시) 보호그룹 공유 → IR 결재 → 할당 → 분기 모니터링 | DX운영 | 1~3영업일 |
| **G2** | 요건 확정 → 운영그룹 주관 → **보호그룹 의견 수렴** → IR 결재 → 할당 → 분기 모니터링 | DX운영+정보보호 | 3~5영업일 |
| **G3** | **보완 이행** → 보호그룹 검토 → 필요시 Committee → 운영성 검토 → IR 결재 → 할당 → **집중 모니터링** | 정보보호+DX운영+(Committee) | 2주 이상 |

`Blocker`가 1건이라도 있으면 **"접수 보류 — 보완 후 재제출"** 을 최상단에 표시한다.

# Tab 3 — Entra App 회수 대상 산출

## 8. 처리 흐름

```
[CSV 업로드 · 복수 파일]
      ▼
[1] RFC4180 파싱 (이중 따옴표·임베드 JSON 대응)
[2] 파일 종류 자동 판별 → appId 기준 병합
[3] 데이터 커버리지 산출 — 무엇이 없어서 무엇을 못 하는지
[4] 처분 판정 D1~D4 + 보안 플래그
[5] 소유자별 그룹핑 → 확인 메일 초안
      ▼
[요약 · 목록 · 메일 · CSV/JSON]
```

## 9. 입력

### 9-1. 두 가지 모드

| 모드 | 입력 | 판정 범위 |
|---|---|---|
| **기본** | M365 관리센터 &gt; 앱 등록 &gt; 관리 목록 내보내기 CSV | 자격증명·리디렉션·태그·멀티테넌트 → **D1/D2/D4** |
| **정밀** | + `collect_entra_inventory.ps1` 산출 CSV (01~05) | Graph 권한·소유자·로그인 활동 → **D3 + 소유자별 메일** |

### 9-2. 파일 종류 자동 판별

| 종류 | 판별 기준 |
|---|---|
| 관리센터 내보내기 | `keyCredentials` + `passwordCredentials` + `appID` |
| 01 앱 요약 | `graphPermissionCount` |
| 02 요청 권한 | `permissionName` + `resourceAppId` |
| 03 소유자 | `ownerObjectId` 또는 `ownerMail`+`appId` |
| 04 동의된 권한 | `grantType` |
| 05 로그인 활동 | `lastSignIn` 또는 `lastAppOnlySignIn` |

**CSV 파싱 주의**: 관리센터 내보내기는 값을 이중 따옴표로 한 번 더 감싸고(`"""TestApp"""`),
`keyCredentials` 등에 JSON을 통째로 넣는다.
파싱 후 리터럴 따옴표를 벗기되 JSON 시작(`[`/`{`)은 건드리지 않는다.

### 9-3. 커버리지 표시 (FR-T3.3)

| 축 | 없으면 못 하는 것 |
|---|---|
| 앱 목록 | 아무 판정도 불가 |
| Graph 권한 | **D3 판정 및 「Graph API 권한 없는 앱」 정의 적용 불가** |
| 소유자 | **확인 메일 생성 불가** |
| 로그인 활동 | 90일 미사용 판정 불가 → 자격증명·구성 상태로 대체 |

부족한 축이 있으면 경고 배너와 함께 수집 방법을 안내한다.

## 10. 처분 판정

```
Graph 권한 보유
  ├─ 미사용 또는 인증 불가 ─────────────────▶ D3  권한 회수 대상
  └─ 정상 ──────────────────────────────────▶ D4  유지
Graph 권한 없음 / 미상
```
